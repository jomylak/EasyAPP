Sixty-five strong matches in one day is still too many to apply to, but it is a completely reasonable number to read. That gap — between what a filter can narrow to and what a person can judge — is the whole design problem, and it is why every day gets its own table rather than one global list with a date column.

Sep 3 is showing Top Prestige while Sep 2 sits on Best Fit, sorted differently, at a different row count. Each day owns its own state — that is the point of the component, and it is why this is not one table with a date column. The chips are not a separate mechanism: pressing one fills in the same threshold boxes, so you can start from a preset and then adjust it.

Two scores, two temperatures

The database already separates fit_score, desirability_score, and company_prestige. They answer different questions, so they should not look alike.

Prestige runs warm — it is about how much a name shines, and you scan it to make sure a Microsoft posting never slips past. Fit runs cool — it is a sober match calculation, and it earns no glow. Desirability, being a blend, stays plain grey text. One glance down the two rightmost columns tells you which kind of day it was, and no legend is required to read it.

Prestige 2→10 in warm, fit 2→10 in cool. Both ramps hold their contrast against the near-black ground; neither is the accent.

The system

ElementDecisionWhy
Row height34px shadcn ships 53px. At 34px a 900px viewport holds ~24 rows, so a day is two scrolls instead of five. Below 30px the checkbox target gets unfair.
Ground#0d1014 Near-black with a cool bias rather than neutral grey — it sits under both score ramps without tinting either.
Accent#4b90d0, selection only The one interaction that matters is ticking a box. The accent is spent entirely on selected state and the Launch button; nothing else competes.
TypeIBM Plex Sans / Mono / Serif Mono on every number, pay range and count so columns align on the digit. Serif only in this document, never in the app.
Separators1px, #1c232b Visible enough to track a row across eight columns, quiet enough that 30 of them do not read as a grid of boxes.
FiltersTyped thresholds Any number, per column, per day — not fixed buckets. A day where nothing clears fit 8 should be answerable by typing 7, without waiting for someone to add a "≥ 7" button.
ExpansionIn place, 220ms slide The specific Intern-list annoyance being fixed. Full description first, then the model's reasoning, then eligibility and the chosen resume — without losing your scroll position. Animated via grid-template-rows: 0fr → 1fr, which animates to content height without hard-coding one; disabled under prefers-reduced-motion.
Cost$0.04/application Held at the configured default until enough runs accumulate to measure it. There are three in the database, all on Claude, so any per-job figure today is a guess and the bar says "default" rather than printing a confident number.
DescriptionsSanitise before render Some rows store escaped markup rather than prose — Adobe's arrives as &lt;div&gt;&lt;p&gt;…. The panel has to unescape and strip tags, not print them, and never inject them as HTML.

What I need from you

  1. The direction itself. Dense dark table, warm prestige and cool fit, accent spent only on selection. Yes, or tell me what to move.
  2. Row height. 34px above. If you want it tighter I can go to 30px; much below that and ticking boxes accurately gets annoying.
  3. The description panel. It scrolls at 200px so one long posting cannot push the next twenty rows off screen. Say if you would rather it ran full length and you scrolled the page instead.
  4. The columns. Company, Title, Location, Pay, Prestige, Fit, Desirability. Missing anything you would triage on — ATS, source board, posting age, job type?

Answer these and the next step is the full three-tab canvas, then the React build. Backend work (Milestone 1) does not depend on any of this and starts now.
